# VASP Error Recovery

This skill is responsible for performing an **evidence-based diagnosis** after VASP errors out, appears stuck, or times out, and then giving **suggested changes** and a judgment on **whether the current task should be stopped**.

It is not a run entry point. Actually starting/rerunning VASP should still be handed to `run-vasp`.

## When to use

Use this skill when any of the following occurs:

- `run-vasp/scripts/check_convergence.py` returns `failed`, `unconverged`, or `incomplete_postprocess`
- `vasp_runner.py` returns a nonzero exit code
- After a GPU/MPI/memory error, you need to decide whether to stop the old task first
- The run has been going too long, and the log, `OUTCAR`, and `OSZICAR` have had no new output for a long time
- The user explicitly says "it errored", "it's stuck", "it timed out", or "should I stop it and rerun"

## Core principles

1. **Diagnose first, act later**
   Before actually stopping a process or modifying inputs, read the state, logs, and `check_convergence` results.

2. **Use the caller's local troubleshooting first, then this skill for unified diagnosis**
   If the upstream workflow ships its own `references/troubleshooting.md` or equivalent local rules, the caller should read it first and digest the task-specific troubleshooting advice; only when a unified judgment is still needed on "whether to terminate the current run, whether it is merely stalled, and how to organize the rerun plan" should this skill be entered.

3. **Only handle tasks with proven ownership**
   If the current task has no `.vasp_run_state.json` generated by `run-vasp`, or process ownership cannot be proven, do not terminate it on your own.

4. **No automatic reruns**
   This skill only outputs suggestions; it does not automatically stop or resubmit tasks without user confirmation.

5. **Termination requires user confirmation**
   If you recommend stopping the current task, you must clearly tell the user:
   - Why you recommend stopping
   - Whether the current run is still alive
   - What you plan to change after stopping
   - What the new `vasp_runner.py` command will be

## Standard procedure

### 1. Collect evidence

Before invoking this skill, if the upstream skill has its own local troubleshooting document, read it first:

- e.g. `relax/references/troubleshooting.md`
- or `workflow-electronic-structure/references/troubleshooting.md`

Then enter this skill for unified diagnosis.

Read first:

- `.vasp_run_state.json` in the current directory
- `OUTCAR`
- `OSZICAR`
- The current main log (prefer the `log_path` recorded in the state)
- Output of `run-vasp/scripts/check_convergence.py`

Recommended to run directly:

```bash
cd "<repo_root>" && python .claude/skills/vasp-error-recovery/scripts/analyze_error.py --work-dir "<task_dir>"
```

### 2. Match the problem type

Using `references/troubleshooting.md`, first determine whether it is one of:

- Electronic (SCF) steps not converging
- Ionic steps not converging
- `ZBRENT`
- Memory/LAPACK errors
- `WAVECAR` mismatch
- `POTCAR` ordering, or a user-specified pseudopotential variant not being carried over
- Abnormal cell changes
- HSE extremely slow or stuck
- Stalled run with no new output for a long time

### 3. Output suggestions

At minimum, tell the user:

- The problem type you identified
- What the evidence is
- Which parameters or inputs you suggest changing
- Whether you recommend stopping the current task first
- If rerunning, whether the old task must be terminated first

### 4. If the user agrees to stop

Only when all of the following conditions are met may you call:

```bash
cd "<repo_root>" && python .claude/skills/run-vasp/scripts/terminate.py --work-dir "<task_dir>" --reason "<reason>"
```

If this is an old, manually launched task without `.vasp_run_state.json`, you must first do a candidate check only:

```bash
cd "<repo_root>" && python .claude/skills/run-vasp/scripts/terminate.py --work-dir "<task_dir>" --allow-cwd-scan --dry-run
```

Only when every candidate PID in the dry-run output shows a cwd exactly equal to `<task_dir>` may you drop `--dry-run` and execute it after the user agrees. Do not switch to `pkill -f` or any command-line pattern matching.

Conditions:

- Ownership evidence for the current run is clear
- The user has explicitly agreed to stop
- You have explained what will be changed after stopping and how to rerun

### 5. Rerun

After stopping, return to the `run-vasp` workflow:

- Modify the inputs
- If `POTCAR` needs to be regenerated, you must call `setup_vasp_inputs`; if the user previously specified a pseudopotential variant, you must pass the same `potcar_overrides` JSON object (e.g. `{"Cr": "Cr_pv"}`) in the same tool call; do not generate, concatenate, or copy `POTCAR` manually with Bash/Python
- Show the user the new `vasp_runner.py` command
- Obtain user confirmation again
- Resubmit

## Prohibited actions

- Do not use fuzzy commands like `pkill`, `killall`, `pkill -f vasp_std`, or `pkill -f "vasp_gpu.*<dir>"`; `pkill -f` may kill the shell/message-reading process that is executing the command
- Do not launch another `mpirun` in the same directory while the old run may still be alive
- Do not conclude that a recalculation is required just from seeing "fatal error"
- Do not automatically terminate + rerun without user consent
- Do not bypass `setup_vasp_inputs` to fix `POTCAR` manually; when the user specified a pseudopotential variant, error recovery and reruns must keep using the same `potcar_overrides`
