# VASP Electronic Structure Workflow

This skill handles the following tasks in one place:

- Static single-point electronic-structure baseline
- Band structure
- Density of states (DOS / PDOS)
- PBE band gap
- High-accuracy HSE band gap

It extends the old `bandgap` workflow rather than fully replacing its run rules. The original requirements on `PBE -> HSE`, `WAVECAR` continuity, a separate confirmation before starting HSE, and confirming the GPU count all still apply.

## Related Skills

- `run-vasp`: the official run entry point; must be used
- `incar-performance`: must be used first whenever the user mentions GPU, `KPAR`, `NCORE`, `NPAR`, or wants hardware-specific tuning
- `workflow-convergence`: recommended to converge `ENCUT/KSPACING` before production electronic-structure comparisons
- `workflow-relax`: if the structure is not yet optimized, relax it first
- `vasp-error-recovery`: diagnosis and recovery for errors, hangs, and timeouts

## Hard Reminder Before Submission

Before submitting any PBE -> HSE band-gap task, explicitly check the PBE `INCAR`:

```text
LWAVE  = .TRUE.
LCHARG = .TRUE.
```

If the PBE input has `LWAVE = .FALSE.` or `LCHARG = .FALSE.`, this is an input error that must be fixed immediately: do not submit the PBE run, and do not use such a PBE result to start HSE.

## Mandatory POTCAR Rules

For electronic-structure, band-structure, DOS, and PBE/HSE band-gap tasks, the POTCAR must be generated by the MCP tool `setup_vasp_inputs` and must use the pymatgen / Materials Project recommended pseudopotentials. Do not switch to bare standard pseudopotentials with the fewest valence electrons to reduce cost.

Requirements:

1. When preparing production PBE/HSE/DOS/band-structure inputs, call `setup_vasp_inputs` to generate the `POTCAR` and a copy of the `POSCAR` in that working directory; do not manually concatenate, copy, edit, or reuse an old `POTCAR`.
2. For p-block elements such as `Ga`, `Ge`, `In`, `Sn`, `Tl`, `Pb` whose semicore d states must be treated as valence, keep the recommended `_d` pseudopotentials; in the current benchmark, specifically confirm `Ga_d`, `In_d`, `Sn_d`, `Pb_d`.
3. The `(Used POTCARs: ...)` returned by `setup_vasp_inputs` must be written to or reported in the task record. If the system contains `Ga/In/Sn/Pb` and the returned value lacks the corresponding `_d`, stop and fix the input; do not proceed to submit VASP.
4. The PBE pre-calculation and the HSE calculation must use the same `POTCAR`, the same structure, and consistent `ENCUT/KSPACING` settings, unless the user explicitly requests a single-variable comparison.
5. Do not reuse input files from historical `runs/bg_*` directories as the starting point for new calculations; old directories may come from the old pseudopotential logic or have been overwritten by later files. When recomputing, regenerate inputs from `data/bandgap/<material>`, the reference structure, or a user-specified structure.

## PBE -> HSE File Retention Rules

When the PBE SCF serves as the pre-calculation for HSE, the wavefunction and charge density must be kept for the HSE warm start:

```text
LWAVE  = .TRUE.
LCHARG = .TRUE.
```

Requirements:

1. When preparing the PBE SCF `INCAR`, do not set `LWAVE = .FALSE.` or `LCHARG = .FALSE.`; if a template or the model produces either value, change it to `.TRUE.` before submitting PBE.
2. Before starting HSE, confirm that non-empty `WAVECAR` and `CHGCAR` exist in the PBE directory. If they are missing, do not continue HSE from that PBE result; rerun PBE first, or explicitly switch to a cold start and state the cost.
3. The HSE stage should warm-start from the PBE `WAVECAR/CHGCAR` and keep the same `POTCAR`, the same structure, and the same `ENCUT/KSPACING` settings.

## Workflow Selection

### A. Static SCF

Use for:
- Final total energy
- Pre-computed charge density and wavefunctions for subsequent DOS / band structure / HSE

Steps:
1. Confirm the structure source
2. Run `workflow-convergence` first if needed
3. Read and write `templates/INCAR_pbe_scf`
4. Generate input files
5. Submit via `vasp_runner.py` in `run-vasp`
6. Check with `run-vasp/scripts/check_convergence.py`
7. If it fails, does not converge, or appears stuck, hand off to `vasp-error-recovery` first

### B. Band Structure / DOS

Typical two-step approach:
1. First run a static SCF to produce a stable `CHGCAR` / `WAVECAR`
2. Then run a non-self-consistent band structure or DOS calculation

Requirements:
- The non-self-consistent stage must not deviate from the core settings of the previous step
- Enable `LORBIT` for projections
- Line-mode band structure requires high-symmetry-path KPOINTS explicitly provided / generated by the user or upstream
- If the non-self-consistent stage exits abnormally or post-processing files are incomplete, first use `vasp-error-recovery` to determine whether it is an input problem, a convergence problem, or merely incomplete post-processing

### C. High-Accuracy HSE Band Gap

Strictly follow:
1. PBE SCF
2. PBE convergence check
3. Prepare HSE inputs
4. **Separately** confirm with the user whether to continue with HSE
5. If GPUs are available, **separately ask for the GPU count**
6. Then submit HSE via `run-vasp`
7. Extract the band gap with `scripts/gap.py`

## Failure and Recovery

Whether static SCF, band structure, DOS, or HSE, if any of the following occurs, hand off to `vasp-error-recovery` first:

- `vasp_runner.py` exits with a non-zero status
- `run-vasp/scripts/check_convergence.py` returns `failed` / `unconverged` / `incomplete_postprocess`
- The log, `OUTCAR`, or `OSZICAR` has had no new output for a long time
- After a GPU / MPI / memory error, you need to decide whether to stop the old job first

The handling order should be:

1. First `Read references/troubleshooting.md`
2. Based on the current stage (PBE / HSE / DOS / band structure), check the most direct local troubleshooting advice
3. If a unified decision is still needed on "whether to keep waiting, whether to terminate, and how to modify and rerun", then call `vasp-error-recovery`

Recommended call:

```bash
cd "<repo_root>" && python .claude/skills/vasp-error-recovery/scripts/analyze_error.py --work-dir "<current task directory>"
```

Based on the output of `vasp-error-recovery`, decide:

- Whether to keep waiting
- Whether to modify `NELM` / `ALGO` / `ISMEAR` / `SIGMA` / HSE parameters
- Whether to recommend terminating the old run before resubmitting

If `vasp-error-recovery` recommends stopping the old run first, you must first explain to the user the evidence, the proposed changes, and the new runner command. Only after the user explicitly agrees may you run:

```bash
cd "<repo_root>" && python .claude/skills/run-vasp/scripts/terminate.py --work-dir "<current task directory>" --reason "<reason for stopping>"
```

**Never** start a second active PBE / HSE / DOS / band-structure job in the same directory while the old run may still be alive.

## Mandatory HSE Rules

1. **A separate confirmation is required before starting HSE**
   After PBE has converged and the HSE input files are ready, you must stop and separately ask the user whether to continue.

2. **Ask for the GPU count when GPUs are available**
   If the user only says "continue" without giving the number of GPUs, do not default to 1 GPU or multiple GPUs.

3. **WAVECAR continuity**
   An HSE warm start requires consistent `ENCUT` and k-point settings between stages; if they differ, do not force a restart from the old `WAVECAR`.

4. **Diagnose errors before deciding whether to stop**
   If HSE fails due to GPU/MPI/memory issues, first use `vasp-error-recovery` to check whether to terminate, then modify parameters and resubmit.

## Recommended Post-processing

Band-gap extraction:

```bash
cd "<repo_root>" && python .claude/skills/workflow-electronic-structure/scripts/gap.py "<vasprun.xml>"
```

## Prohibited Actions

- Do not hand-write production `mpirun ... vasp_std/vasp_gpu` commands
- Do not start a second active VASP process in the same directory
- Do not start HSE without user confirmation
- Do not skip `incar-performance` when the user asks for hardware-specific tuning
- Do not skip `vasp-error-recovery` and directly apply vague termination or blind reruns to a failed or seemingly stuck old run
